# T011: Add a versioned signal registry and RINEX 2 adapters

[Task index](../../ROADMAP.md).

## Objective

Validate constellation/version/tracking combinations; support P1/P2 and explicit P1-C1/P1-P2 bridges without guessing tracking identity.

## Context

The repository already has signals.py and quality.py; the old 'new signal module' target should be reconciled with that structure. Supported tracking identities and RINEX-version adapters must remain explicit.

## Scope

`gnss_tec/configuration.py`, `gnss_tec/calculation/tec.py`, new signal module. The existing `gnss_tec/signals/selection.py` is the first candidate for extension; a new signal module is only a proposal.

## Implementation Plan

1. Inventory the existing signal registry/candidate rules and supported RINEX 2/3 inputs; document ambiguous legacy tracking identities and current bias coverage.
2. Propose versioned constellation/tracking entries with frequency, phase-partner and bias mapping, plus explicit P1/P2 and P1-C1/P1-P2 bridge rules. Do not guess a tracking identity.
3. Obtain review of the signal/adapter and public support contract; extend the existing signal module unless a separate module has a demonstrated need.
4. Validate each supported pair and adapter with independent frequencies, phase associations, bias signs/bridges and unsupported-combination errors; publish the support table.

## Acceptance Criteria

- [ ] every supported pair has frequency, phase-partner and bias tests.
- [ ] Legacy bridges have explicit provenance/validity and unsupported or ambiguous tracking combinations are rejected clearly.

## Validation

Use RINEX 2/3 fixtures and pair-specific frequency/phase/bias checks. Retain complete-candidate fallback and signal-switch arc tests; test supported and deliberately ambiguous combinations.

## Progress & Handoff

**Next:** Inventory current signals.py and legacy-adapter contracts. Versioning, tracking identity and bridge semantics need review before extension.
