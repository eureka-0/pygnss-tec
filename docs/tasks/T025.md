# T025: Gate publishing on installed-artifact validation

[Task index](../../ROADMAP.md).

## Objective

Prepare consistent 0.5.0 metadata and gate publishing on clean installation and validation of the exact artifacts being released.
Verify dependency/type metadata, locked release builds, imports and minimal RINEX-to-TEC; exercise free-threaded artifacts separately.

## Context

Release gates must validate the exact artifacts being published, in clean installed environments.
At the 2026-10-18 review of `2370e03`, Python/Rust manifests and lockfiles still declared 0.4.2 and the changelog remained Unreleased.
Local release wheel/sdist construction, two clean-wheel environments with 265 tests each and existing compatibility CI passed for that candidate.
Those results do not validate 0.5.0 artifacts or the complete publishing matrix, including free-threaded and 32-bit installations.

Workflow design and artifact plumbing can proceed independently of the scientific fixes.
Publication must additionally verify the release safeguards from T031, T006 and T009; their broader task completion is not a prerequisite for drafting the gate.

## Scope

`.github/workflows/publish.yml`, `.github/workflows/test.yml`, reusable validation helpers/workflows, `pyproject.toml`, `Cargo.toml`, `uv.lock`, `Cargo.lock` and `CHANGELOG.md`.
Keep scientific fixture ownership with T031/T006/T009 and consume their permanent regression checks in artifact validation.

## Implementation Plan

1. Review the supported OS/architecture/interpreter matrix and publication wiring before changing release behavior.
   Record how each ordinary, free-threaded and 32-bit artifact will be installed and exercised; unsupported targets require an explicit support decision rather than a skipped check counted as success.
2. Update both project versions and corresponding lockfile entries to 0.5.0 without unrelated dependency upgrades, then finalize release notes and migration guidance.
   Check tag/manifest/lockfile agreement before publishing and verify the same version in wheel and sdist metadata.
   Preserve the documented API removals, default continuity behavior and scientific/input limits in the release notes.
3. Build release artifacts with locked dependencies and record the candidate commit, build settings, artifact names and hashes.
   Pass the same uploaded artifacts to isolated validation jobs; do not rebuild a replacement wheel and assume it validates the published one.
4. Install each retained wheel in a clean consumer outside the source tree and verify import location, public API, dependencies, `py.typed`, stubs and minimal scientific outputs.
   Run the permanent T031/T006/T009 safeguards, checking failure/status/null semantics as well as successful input.
   Validate an sdist consumer build and separately exercise supported free-threaded artifacts; inspect actual GIL/runtime/dependency behavior instead of inferring support from a wheel filename.
5. Add a non-publishing workflow entry point and make publication require version consistency and successful artifact/scientific validation.
   Verify that version mismatch, failed installation or a failed safeguard blocks the publish job, with credentials/permissions confined to the publication path.
6. Exercise the supported matrix without uploading to PyPI and retain exact-artifact hosted results, including explicit unsupported-target decisions.
   Complete publication only after all 0.5.0 release checks are verified; passing checkout tests or inspecting YAML alone is insufficient.

## Acceptance Criteria

- [ ] Manifests, lockfiles, tag, changelog and artifact metadata agree on 0.5.0; mismatches prevent publication.
- [ ] Locked release wheel/sdist builds preserve required sources/type files and avoid unrelated dependency changes or local temporary files.
- [ ] Publication depends on clean installation and successful validation of the exact artifacts being released, including the reviewed T031/T006/T009 release safeguards.
- [ ] Provenance identifies the commit, settings and hashes of tested/released artifacts; sdist and free-threaded checks are separate from ordinary wheel checks.
- [ ] Every retained publishing target has actual installation/runtime results; excluded targets have a reviewed support decision and are not advertised as validated.
- [ ] A non-publishing matrix run passes, and deliberate version/install/safeguard failures demonstrably block the publication path.

## Validation

Use clean installed-artifact consumers, metadata/type-file checks and small independent scientific input/output assertions.
Verify source-tree isolation, API removals, version mismatch failures, artifact hashes and the scientific failure controls before any upload.
Check workflow dependency wiring and actual hosted results; a local checkout test or YAML inspection alone does not close this task.
Keep the supported matrix and reproducible checks in tracked CI/tests or release documentation rather than depending on temporary local reports.
